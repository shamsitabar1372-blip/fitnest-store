راهنمای اجرای بک‌اند فروشگاهی فیت‌نست پرو

این سند مربوط به بک‌اند جدید جنگو است. سرور قدیمی صرفاً پیش‌نمایش باقی می‌ماند. همهٔ دستورها باید از پوشهٔ پروژه اجرا شوند. متن فارسی راست‌به‌چپ و دستورهای قابل کپی چپ‌به‌راست هستند.

معماریاجرای محلیداکر و دیتابیسمدیریترابط برنامه‌نویسیامنیت و ورودپرداخت و ارسالاستقرارپشتیبان‌گیریآزمون‌هاانتقال داده‌ها
وضعیت تحویل: مدل‌ها، APIهای اصلی، پنل، اتصال فرانت‌اند و آزمون‌های خودکار پیاده‌سازی شده‌اند. پیامک واقعی، درگاه پرداخت، تعرفهٔ تیپاکس و انتشار عمومی فعال نشده‌اند. وجود کد و موفقیت آزمون محلی، گواه آماده‌بودن استقرار تولید یا آزمون نفوذ کامل نیست.

۱. معماری و مرز اعتماد

فرانت‌اند موجود شامل صفحهٔ اصلی و فایل‌های جاوااسکریپت و سبک محلی حفظ شده است. جنگو همان صفحه را سرو می‌کند و اتصال سروری را به آن اضافه می‌کند. در این حالت محصولات، گونه‌ها، قیمت، سبد، نشانی، سفارش و دیدگاه از API واقعی دریافت می‌شوند. دادهٔ مرورگر مرجع قیمت، موجودی، هویت یا پرداخت نیست.

Browser → Django /api/ → PostgreSQL
               ├─ session + CSRF + permissions
               ├─ shop/services.py: pricing, stock, checkout
               ├─ shop/otp.py: server-side SMS
               └─ shop/payments.py: disabled gateway contract

/       storefront
/ops/   Persian operations dashboard
/admin/ authenticated catalog and configuration forms

نسخهٔ جنگو از شاخهٔ پشتیبانی بلندمدت ۵٫۲ انتخاب و نسخهٔ نصب‌شده در فایل وابستگی قفل شده است. دیتابیس تولید PostgreSQL است؛ SQLite فقط با انتخاب صریح حالت محلی فعال می‌شود. کانتینر برای Python ۳٫۱۳ تنظیم شده است. روی این سیستم Python ۳٫۱۵ موجود بود و آزمون محلی با آن اجرا شد؛ برای محیط اصلی، نسخهٔ کانتینر مبناست.

بخشمدل‌ها و رفتار
کاتالوگدستهٔ سلسله‌مراتبی، محصول، ویژگی JSON، تصاویر چندگانه، گونه با رنگ و اندازه و شناسهٔ انبار
قیمتعدد صحیح ریالی، تخفیف زمان‌دار، نمایش تومان در رابط، محاسبهٔ مالیات و ارسال در سرور
سبدمالکیت نشست مهمان یا مشتری؛ انتقال فقط بعد از تأیید پیامکی؛ نگهداری سبد پرداخت‌نشده
سفارشتصویر ثابت اقلام و نشانی، کد یکتا، کلید تکرارناپذیری درخواست، رزرو موجودی و انقضا
مدیریتمجوزهای نقش، ثبت رویداد بدون کلید و متن حساس، گزارش فروش تأییدشده و هشدار موجودی

موجودی هنگام ثبت سفارش برای ۲۰ دقیقه رزرو می‌شود. سفارش پرداخت‌نشده، سبد را حذف نمی‌کند و تغییر آن تا لغو یا پایان رزرو محدود می‌شود. پس از تأیید سروری پرداخت، اقلام خریداری‌شده از سبد حذف می‌شوند. اجرای دوره‌ای فرمان انقضا ضروری است. کد تخفیف سفارش‌های لغوشده یا مرجوع‌شده از سهمیهٔ مصرف کنار گذاشته می‌شود؛ سفارش‌های در انتظار پرداخت سهمیه رزرو می‌کنند.

۲. اجرای محلی در ویندوز

نصب Python و اینترنت برای دریافت وابستگی‌ها لازم است. اجرا فقط روی حلقهٔ محلی سیستم انجام می‌شود و سایتی منتشر نمی‌شود. رمز یا کلید واقعی برای این مرحله لازم نیست.

cd 'D:\Website tesy gigi'
python -m venv .venv
.venv/Scripts/python -m pip install -r backend/requirements.txt
$env:DJANGO_LOCAL = '1'
$env:DJANGO_DEBUG = '1'
.venv/Scripts/python backend/manage.py migrate
.venv/Scripts/python backend/manage.py setup_roles
.venv/Scripts/python backend/manage.py collectstatic --noinput
.venv/Scripts/python backend/manage.py runserver 127.0.0.1:8081 --noreload

اسکریپت زیر همین مراحل پایه را انجام می‌دهد. حالت محلی یک کلید تصادفی خصوصی در پوشهٔ خصوصی می‌سازد. دیتابیس محلی نیز همان‌جا ذخیره می‌شود. فایل نمونهٔ متغیرهای محیطی توسط جنگو خودکار بارگذاری نمی‌شود؛ در اجرای مستقیم باید متغیرها را در محیط پردازش تنظیم کنید. Docker Compose فایل محیطی را می‌خواند.

powershell -File scripts/run-backend.ps1

برای کاتالوگ نمایشی اختیاری:

.venv/Scripts/python backend/manage.py seed_demo

دادهٔ نمونه صریحاً برچسب‌گذاری می‌شود، موجودی اولیه صفر است، تیپاکس نیازمند تعیین هزینه است و پذیرش سفارش خودکار فعال نمی‌شود. این فرمان حساب مشتری، کد ورود یا پرداخت نمونه ایجاد نمی‌کند. اجرای دوباره، محصول موجود را بازنویسی نمی‌کند.

برای ساخت مدیر محلی، خودتان رمز را در فرمان تعاملی تعیین کنید؛ رمز آماده یا حساب مخفی وجود ندارد:

.venv/Scripts/python backend/manage.py createsuperuser

پس از اجرا صفحهٔ فروشگاه را از آدرس سرور باز کنید؛ بازکردن فایل مستقیم، اجرای بک‌اند نیست. اگر پورت اشغال است، عدد پورت را تغییر دهید. سرویس پیش‌نمایش قبلی روی پورت دیگر می‌تواند مستقل باقی بماند.

۳. PostgreSQL و Docker Compose

Docker Desktop یا Docker Engine و افزونهٔ Compose باید نصب باشند. فایل نمونه را کپی کنید و فقط روی سیستم خودتان مقدارهای خالی را پر کنید. فایل واقعی نباید وارد گیت شود.

Copy-Item .env.example .env
python -c "import secrets; print(secrets.token_urlsafe(64))"

خروجی تصادفی را به‌عنوان کلید جنگو در فایل خصوصی قرار دهید. رمز دیتابیس نیز باید مستقل و تصادفی باشد. نام دیتابیس، نام کاربر و میزبان‌های مجاز را متناسب با محیط تعیین کنید. برای پیش‌نمایش محلی داکر، حالت محلی را صریحاً فعال کنید و موتور دیتابیس را PostgreSQL نگه دارید. برای تولید حالت محلی و اشکال‌زدایی باید خاموش باشند.

docker compose build
docker compose up -d db
docker compose run --rm web python manage.py migrate
docker compose run --rm web python manage.py setup_roles
docker compose run --rm web python manage.py collectstatic --noinput
docker compose run --rm web python manage.py createsuperuser
docker compose up -d web

دیتابیس پورت عمومی ندارد. پورت وب فقط به حلقهٔ محلی میزبان متصل است. دادهٔ دیتابیس، تصاویر بارگذاری‌شده و فایل‌های ثابت در حجم‌های پایدار جداگانه نگهداری می‌شوند. حذف حجم‌ها باعث از دست رفتن داده می‌شود؛ برای به‌روزرسانی معمول نباید آن‌ها را حذف کنید.

۴. پنل و نقش‌ها

داشبورد فارسی در مسیر مدیریت عملیاتی است. فرم‌های جزئیات و ویرایش داده با همان سبک تیره در مدیریت جنگو قرار دارند. طرح‌های مفهومی و مجموعهٔ پرامپت‌ها در پوشهٔ طراحی ذخیره شده‌اند؛ گالری شش طرح را ببینید. این تصاویر جایگزین رابط تعاملی نشده‌اند.

نقشدسترسی
ابرمدیرساخت کارکنان، تعیین عضویت نقش و تنظیم مجوزها؛ باید حساب محدود و محافظت‌شده باشد.
مدیر فروشگاهکاتالوگ، موجودی، تخفیف، تنظیمات، مشتریان با دسترسی مشاهده، سفارش و گزارش؛ تغییر کلید یا اعلام دستی پرداخت موفق ندارد.
کارمند فروشگاهمشاهدهٔ محصول، دسته، موجودی و سفارش؛ انتقال وضعیت سفارش پرداخت‌شده به آماده‌سازی، ارسال و تحویل؛ بدون مشاهدهٔ فهرست مشتریان یا تنظیمات مالی.

ابرمدیر باید پرچم کارمند را برای حساب مدیریتی فعال و نقش مناسب را جداگانه اختصاص دهد. نقش به‌تنهایی ورود مدیریتی را فعال نمی‌کند. مشتری پیامکی معمولی هیچ نقش مدیریتی نمی‌گیرد. تأیید شماره، تأیید هویت حقوقی یا کد ملی نیست.

موجودی موجود را از بخش اصلاح موجودی با عدد مثبت یا منفی تغییر دهید. این کار با قفل دیتابیس و ثبت رویداد انجام می‌شود. برای محصول: دسته، عنوان انگلیسی، نام فارسی، توضیح، وضعیت و سپس گونه و تصاویر را ثبت کنید. قیمت‌ها به ریال‌اند. ترتیب تصویر، ترتیب گالری را تعیین می‌کند. جدول اندازه و جنس در ویژگی‌ها قرار می‌گیرند؛ محتوای HTML در توضیحات اجرا نمی‌شود.

  "روش شست‌وشو": "مطابق برچسب محصول",

فرم مرجوعی صرفاً درخواست مشتری و نتیجهٔ بررسی را ثبت می‌کند؛ پذیرش درخواست به‌معنای بازپرداخت بانکی نیست. بازپرداخت خودکار تا انتخاب درگاه و پیاده‌سازی مسیر مالی آن فعال نیست. حذف سوابق مالی و تغییر دستی مبلغ یا وضعیت پرداخت در پنل عمومی مجاز نشده است.

۵. API و قرارداد داده

فهرست مسیرها، روش درخواست و نمونهٔ بدنه‌ها در قرارداد ماشینی API قرار دارد. نشست کوکی‌محور و هم‌مبدأ است. ابتدا مسیر نشست را بخوانید تا کوکی CSRF ایجاد شود؛ برای تمام درخواست‌های تغییردهنده، مقدار آن را در سربرگ مربوط بفرستید. شناسهٔ مشتری در بدنه تعیین‌کنندهٔ مالکیت نیست.

GET /api/auth/session
Cookie: csrftoken=...

POST /api/cart
Content-Type: application/json
X-CSRFToken: <value of csrftoken cookie>

{"variantId": 12, "quantity": 2}

عدد گونه در مثال فقط شکل داده را نشان می‌دهد؛ شناسهٔ واقعی را از کاتالوگ دریافت کنید. قیمت ارسالی مرورگر نادیده گرفته می‌شود. تعداد صفر، ردیف همان سبد را حذف می‌کند. افزودن گونهٔ غیرفعال یا تعداد بیش از موجودی پذیرفته نمی‌شود. فهرست محصولات با صفحه‌بندی دریافت می‌شود و رابط همهٔ صفحه‌ها را بارگذاری می‌کند. پنل سفارش‌ها، ۱۰۰ سفارش آخر را همراه آرشیو کامل مدیریت نمایش می‌دهد.

POST /api/checkout/quote
{"addressId":"...","shippingId":1,"coupon":""}

POST /api/orders/create
{
  "addressId":"...",
  "shippingId":1,
  "coupon":"",
  "idempotencyKey":"a new UUID generated for this checkout attempt"
}

محاسبهٔ پیش‌فاکتور رزرو قیمت یا موجودی نیست. ثبت سفارش دوباره قیمت، وضعیت محصول، موجودی، نشانی و قوانین تخفیف را بررسی می‌کند. تلاش مجدد همان درخواست باید همان کلید یکتا را ارسال کند. پاسخ فهرست سفارش‌ها مبلغ را در نگاه اول نشان نمی‌دهد؛ مبلغ و نشانی فقط در جزئیات فاکتور متعلق به همان مشتری بازگردانده می‌شوند.

۶. ورود پیامکی و امنیت

فرایند جدید پیامکی با نشست جنگو کار می‌کند. کد چهاررقمی رمزنگارانه تولید می‌شود؛ فقط خلاصهٔ کلیددار آن در دیتابیس قرار می‌گیرد. کد در پاسخ API، رابط یا لاگ نمایش داده نمی‌شود. مدت اعتبار سه دقیقه، سقف تلاش هر کد پنج بار و فاصلهٔ ارسال مجدد حداقل ۶۰ ثانیه است. محدودیت ارسال برای شماره، نشانی اینترنتی و کل سامانه در دیتابیس نگهداری می‌شود و با راه‌اندازی مجدد پاک نمی‌شود. بعضی سهمیه‌ها پنجرهٔ زمانی ثابت دارند؛ محدودیت جداگانهٔ ارسال مجدد، فاصلهٔ واقعی را کنترل می‌کند.

کنترلمقدار
شمارهحداکثر ۳ ارسال در پنجرهٔ ۱۵ دقیقه و ۱۰ ارسال در روز
نشانی اینترنتی۱۰ ارسال در ساعت، ۳۰ در روز؛ حداکثر ۴۰ تلاش تأیید در ۱۵ دقیقه
کل سامانه۲۰۰ ارسال در روز؛ برای شروع محدود و قابل تغییر در کد
ورود مدیریت۱۰ درخواست ورود در ۱۵ دقیقه برای هر نشانی اینترنتی؛ به‌علاوه حفاظت لایهٔ پراکسی توصیه می‌شود
نشستمشتری واردشده: ۱۲ ساعت؛ سبد مهمان: نشست پایدار تا ۳۰ روز

برای پیامک واقعی، حساب کاوه‌نگار با سرویس اعتبارسنجی، الگوی تأییدشده و اعتبار کافی لازم است. نام الگو و کلید فقط در محیط سرور تنظیم می‌شوند. علاوه بر کلید، فعال‌سازی صریح ارسال لازم است. بدون آن پاسخ در دسترس‌نبودن سرویس برمی‌گردد؛ ورود جایگزین یا کد ثابت وجود ندارد.

KAVENEGAR_API_KEY=
KAVENEGAR_OTP_TEMPLATE=
SMS_ENABLED=0

پس از ارائهٔ اطلاعات و اجازهٔ صریح شما، فعال‌سازی و آزمون تحویل واقعی جداگانه انجام می‌شود. ارسال پذیرفته‌شده توسط ارائه‌دهنده، به‌تنهایی تحویل پیامک را تضمین نمی‌کند. برای مقیاس عمومی، افزایش طول کد به شش رقم، سامانهٔ تشخیص سوءاستفاده و کنترل‌های لبه باید با طراحی رابط هماهنگ شوند.

کوکی نشست در تولید فقط روی HTTPS ارسال می‌شود و دسترسی جاوااسکریپت به آن بسته است. CSRF، کنترل میزبان، مجوز نقش و کنترل مالکیت سمت سرور اعمال می‌شوند. بدنهٔ API محدود است. کلید، شمارهٔ کد و محتوای حساس در رویداد مدیریتی ثبت نمی‌شوند. رویدادها جایگزین پایش زیرساخت یا ممیزی مستقل نیستند.

۷. پرداخت، تیپاکس و نقشه

درگاه واقعی انتخاب نشده است. آغاز پرداخت و بازگشت درگاه وجود دارند، اما غیرفعال‌اند و هیچ پاسخ موفقیت نمایشی تولید نمی‌کنند. قرارداد داخلی درگاه، مبلغ، واحد پول، شناسهٔ درخواست و مرجع تأیید را دارد. تأیید سروری با قفل سفارش و پرداخت، تطبیق مبلغ و جلوگیری از تکرار طراحی و با ارائه‌دهندهٔ آزمایشی داخل آزمون بررسی شده است. آن ارائه‌دهنده در اجرای سایت ثبت نشده است.

برای اتصال واقعی: ارائه‌دهنده و حساب پذیرندگی را تعیین کنید، مستندات امضای درخواست و تأیید را بررسی کنید، کلید را در محیط سرور قرار دهید و سپس آداپتر همان ارائه‌دهنده را بسازید. دامنهٔ بازگشت باید ثابت و HTTPS باشد. مبلغ ریال یا تومان و سیاست تأیید دیررس، تسویه و بازپرداخت باید با همان درگاه تطبیق داده شوند. هیچ کلید ساختگی یا لینک بانکی نمونه به کاربر نشان داده نمی‌شود.

تیپاکس اکنون روش ارسال قابل تنظیم است و اتصال زنده به سامانهٔ حمل ندارد. هزینه باید ثابت و مشخص یا از سرویس مجاز استعلام شود. تا وقتی هزینه نیازمند استعلام است، سفارش با هزینهٔ صفر فرضی نهایی نمی‌شود. تعرفه، مناطق پوشش، رهگیری و قرارداد حمل برای اتصال واقعی لازم‌اند.

انتخاب نقشهٔ قبلی حفظ شده است و ثبت نشانی بدون مختصات نیز از API ممکن است. نقشهٔ وب نشان به کلید عمومی محدود به دامنه و اینترنت نیاز دارد. جست‌وجوی دقیق نشانی وابسته به سرویس نشان است؛ در نبود اتصال معتبر، انتخاب شهر و ورود دستی نشانی جایگزین‌اند. کلید خدمات خصوصی نباید در مرورگر مشتری قرار گیرد؛ پیکربندی خدمات نقشهٔ تولید همچنان به اتصال سروری تأییدشده نیاز دارد.

۸. آماده‌سازی استقرار

  1. هاست دارای اجرای پایدار Python یا VPS با کانتینر، PostgreSQL پایدار و گواهی معتبر HTTPS آماده کنید. هاست صرفاً استاتیک برای این نسخه کافی نیست.
  2. حالت محلی و اشکال‌زدایی را خاموش کنید؛ کلید تصادفی و مستقل، میزبان مجاز، مبدأ CSRF و تنظیمات دیتابیس را وارد کنید.
  3. Gunicorn را پشت پراکسی معکوس اجرا کنید. سرور توسعهٔ جنگو و سرور پیش‌نمایش قبلی سرور تولید نیستند.
  4. فقط وقتی پراکسی مورد اعتماد سربرگ پروتکل را بازنویسی می‌کند، اعتماد به پروتکل پراکسی را فعال کنید. برای نشانی واقعی مشتری، فقط شبکه یا نشانی دقیق پراکسی را در فهرست مورد اعتماد قرار دهید.
  5. فایل نمونهٔ پراکسی در پوشهٔ استقرار است. حجم تصاویر را به مسیر خواندنی پراکسی متصل کنید؛ بارگذاری‌ها نباید به‌صورت اسکریپت اجرا شوند. حجم فایل، دسترسی مدیریت و محدودیت درخواست لایهٔ لبه را تنظیم کنید.
  6. فرمان‌های migration و فایل‌های ثابت را اجرا کنید. پس از تغییر CSS یا جاوااسکریپت پنل، فایل‌های ثابت باید دوباره جمع‌آوری شوند.
  7. فرمان انقضا و پاک‌سازی را هر دقیقه و فرمان پاک‌سازی نشست‌ها را روزانه زمان‌بندی کنید.
  8. دادهٔ واقعی محصول، تصویر، اندازه، موجودی، قیمت، مالیات، ارسال و سیاست مرجوعی را ثبت و بازبینی کنید. دادهٔ نمونه در تولید قابل سفارش نیست.
  9. نسخهٔ PostgreSQL، بازگردانی پشتیبان، قفل‌گذاری هم‌زمان، HTTPS، مجوزها و تست مرورگر را روی محیط پیش‌استقرار بررسی کنید. سپس فقط با اجازهٔ صریح انتشار دهید.
python backend/manage.py check --deploy
python backend/manage.py migrate --check
python backend/manage.py collectstatic --noinput
python backend/manage.py expire_orders
python backend/manage.py clearsessions

تنظیمات HSTS فقط در تولید فعال می‌شود و زیردامنه‌ها خودکار مشمول نشده‌اند. شبکهٔ مستقیم دیتابیس نباید عمومی باشد. خروجی خطای داخلی برای کاربر عمومی جزئیات تنظیمات را نشان نمی‌دهد. برای استقرار واقعی، هشدارهای بررسی تولید باید با توجه به توپولوژی شبکه ارزیابی شوند.

۹. پشتیبان‌گیری و بازگردانی

اسکریپت پشتیبان از ابزار رسمی PostgreSQL داخل کانتینر استفاده می‌کند و رمز را وارد آرگومان فرمان یا خروجی نمی‌کند. خروجی در پوشهٔ خصوصی میزبان ذخیره می‌شود.

powershell -File scripts/backup-postgres.ps1

از دیتابیس و حجم تصاویر به‌صورت روزانه پشتیبان بگیرید؛ نسخهٔ قبل از migration را هم نگه دارید. پشتیبان شامل دادهٔ مشتری است و باید با ابزار رمزگذاری معتبر، دسترسی حداقلی و نسخهٔ خارج از میزبان نگهداری شود. فایل محیطی و کلیدها را مستقل و رمزگذاری‌شده نگهداری کنید. دورهٔ نگهداری و حذف را بر اساس نیاز فروشگاه تعیین کنید.

بازگردانی را ابتدا روی دیتابیس جداگانه و بدون اتصال پرداخت و پیامک آزمایش کنید. فایل dump را با فهرست ابزار رسمی بررسی، سپس روی دیتابیس خالی بازیابی کنید. پس از بازیابی، تعداد سفارش‌ها، جمع مبالغ، تصاویر و حساب مدیریتی را بررسی کنید. این تحویل ادعا نمی‌کند که پشتیبان واقعی سرور شما تهیه یا بازیابی شده است؛ سرور تولید هنوز در اختیار نیست.

pg_restore --list backup.dump
pg_restore --no-owner --dbname=isolated_restore_database backup.dump

۱۰. آزمون و تحویل

$env:DJANGO_LOCAL = '1'
.venv/Scripts/python backend/manage.py test shop --verbosity 2
.venv/Scripts/python backend/manage.py makemigrations --check --dry-run
.venv/Scripts/python backend/manage.py check
python scripts/audit-store-backend.py
python scripts/package-backend.py

آزمون‌ها از دیتابیس موقت، پیامک جایگزین و درگاه جایگزین صرفاً داخل تست استفاده می‌کنند؛ هیچ پیامک یا تراکنش واقعی ایجاد نمی‌کنند. آزمون رقابت بر سر آخرین موجودی فقط روی دیتابیس دارای قفل ردیفی اجرا می‌شود و در SQLite کنار گذاشته می‌شود. فایل گردش کار گیت‌هاب، اجرای PostgreSQL را آماده می‌کند؛ تا اجرا و تأیید خروجی آن نباید آن را موفق فرض کرد.

بستهٔ منبع از فهرست مجاز ساخته می‌شود و دیتابیس، فایل محیطی واقعی، محیط مجازی، آپلود مشتری و پوشهٔ خصوصی را شامل نمی‌شود. بستهٔ قدیمی استاتیک، جایگزین بستهٔ جدید جنگو نیست. خلاصهٔ نتیجهٔ واقعی آزمون‌های این تحویل در فایل نتیجهٔ بررسی کنار این راهنما ثبت می‌شود.

۱۱. انتقال از نسخهٔ قبلی

آخرین پایهٔ بررسی‌شدهٔ گیت‌هاب، commit زیر بود. فایل‌های جدید در پروژه پیاده‌سازی شده‌اند؛ انتشار یا ارسال این مرحله به گیت‌هاب بخشی از اجرای خودکار فعلی نیست.

c770df0a5d395ac978f3e0c43ab6400526da8144

فایل ورود قبلی و SQLite آن به‌عنوان سابقهٔ پیش‌نمایش باقی می‌مانند. نشست‌های قدیمی به جنگو منتقل نمی‌شوند و مشتری باید مجدداً شماره را تأیید کند. سفارش یا پرداخت ذخیره‌شده در مرورگر به سفارش واقعی تبدیل نمی‌شود. نشانی‌های مرورگری نیز بدون احراز مالکیت وارد دیتابیس نمی‌شوند؛ کاربر می‌تواند پس از ورود دوباره آن‌ها را ثبت کند. این تصمیم از تبدیل دادهٔ قابل دستکاری به سابقهٔ مالی جلوگیری می‌کند.

بستهٔ جدید کیفیت یا ابعاد تصاویر اصلی را تغییر نمی‌دهد. فایل‌های بهینه‌شدهٔ بدون اتلاف و تصویرهای اصلی فعال دوباره فشرده یا کوچک نشده‌اند.
